# 交接书 · 给网页端 GPT

> 这份文件在站点上：`https://celine-ryan-world.vercel.app/handbook/交接-GPT.md`
> 你（网页端 GPT）读这一个文件就够了。它说明**你负责什么、我负责什么、我们怎么对接**。

---

## 一、两个工位

| | **你（网页端 GPT）** | **我（作者本机的 AI）** |
|---|---|---|
| 位置 | 网页，只能访问这个站点 | 作者电脑上，能读写项目文件 |
| 强项 | 读得广、写得快、能从外部视角挑毛病、能同时看很多分册 | 能改库、能跑工具、能出决定卡、能做全库扫描 |
| **能读** | 站点上的一切（见第二节） | 本地全部文件，包括小说原文 |
| **能写** | **什么都写不了**——站点是只读的静态站 | 只能通过「决定卡」改库，且必须有作者批准 |
| 谁来传话 | 作者 | 作者 |

**一句话**：你是**外部大脑**，我是**本地的手**。我们之间没有网络直连，**作者是唯一的搬运工**。

## 三、你不能做什么（做了会被打回）

| 禁止 | 为什么 |
|---|---|
| 直接改库 | 站点是静态的，你没有写入通道；所有改动都要过作者 |
| 引用小说原文 | `source/` 小说原文**从未公开**，站点上没有。你若「读到」了原文，那是你在编 |
| 凭空补设定 | 站点上没有的，就是库里没有。缺了就说缺了，别自己填 |
| 跨时代引用 | **这是最硬的一条**。见第六节 |
| 假装改完了 | 你产出的是**提案**，不是改动。落库由我在本地做，作者点头才生效 |

## 四、你的三种产出

### 产出 A · 写作稿（对应「按主题出创作包来写」）

1. 读 `/packs/index.md` 选包。包名格式是 `P____`，每个包标注了**实体 · 时代 · 截至时间点**。
2. 选题要落在**某个具体时代**。例如「洛蒂在庭院的第一天」＝ 后日谈。
3. **只许用你选中的那些包里的内容。** 包里没有的设定不许编。
4. 交稿时附上用了哪些包号。

> 包的「截至时间点」是硬约束：那个时间点还没发生的事，包里不会有，你也不能写。

### 产出 B · 审库提案（对应「外部 AI 审库 → 提建议 → 落库」）

从 `/review/` 挑一册逐字读完，找这几类问题：

- **矛盾**：两条事实互相打架
- **时间错位**：某件事挂在明显不对的时间点上
- **时代泄漏**：后日谈的内容混进了主线/历史时代的分页
- **命名不一**：同一个东西两种叫法
- **缺失**：明显该有却没有的条目

按第五节格式逐条产出。**宁缺毋滥**，3~5 条扎实的比 20 条含糊的有用。

### 产出 C · 测试报告（验证站点本身好不好用）

作者会给你具体测试单。你如实报告：读到了什么、哪里读不到、哪里对不上、哪里让你怀疑。

## 五、提案格式（**严格照抄，我要用它生成决定卡**）

一条提案一个 JSON 块。作者会把它复制给本地的我。

```json
{
  "proposal_id": "GPT-20260911-001",
  "from": "ChatGPT (web)",
  "date": "2026-09-11",
  "kind": "fact_edit",
  "target": {
    "entity": "洛蒂",
    "fact_id": "fact_00233",
    "match": "该事实里独一无二的一小段原文"
  },
  "problem": "这句话和什么对不上——一句话说清",
  "suggestion": "建议改成什么；如果是删，写「删除」",
  "evidence": "依据：站点上哪个文件、哪一句话、为什么这样才对",
  "confidence": "high"
}
```

**字段说明**

| 字段 | 取值 |
|---|---|
| `kind` | `fact_add` / `fact_edit` / `fact_delete` / `entity_edit` / `relation_add` / `relation_edit` / `note` |
| `target.entity` | 实体名，必须和站点上的条目名完全一致 |
| `target.fact_id` | 站点上每条事实前面那个 `fact_01234`；不确定就留空，但 `match` 必须填 |
| `target.match` | 从原文里摘一段**独一无二**的话。摘得重复了我会退回 |
| `confidence` | `high`（我基本确定）/ `medium` / `low`（只是怀疑） |

**几条硬要求**

- **一条一个问题**。别把三处改动塞进一条。
- `evidence` 必须指向**站点上的具体位置**。「我觉得应该……」不算依据。
- 拿不准的写 `"confidence": "low"`，我会重点核。**不要为了凑数把 low 写成 high。**
- 你**不需要**给出决定卡号、sha256、卡格式——那些是我这边的活。

## 六、六条铁律（我会照着校验，违反的一律打回）

1. **时代隔离**（最硬）。三个时代是 `history`（历史）/ `mainline`（主线）/ `afterstory`（后日谈）。
   后日谈的稿子里不许出现只有主线/历史才知道的事；主线的稿子里不许用后日谈的结局。
   每个包都标了自己的时代，**只许用同代内容**。
2. **正文零标注**。正文是条目式的平实文字，不能出现 `【】`、`**`、`※`、`（第X章）` 这类标记。
   出处、状态、时代都放字段里，不放正文里。
3. **事实要可检索**。可以写成一条独立断言的东西才进事实层，别写成散文。
4. **不臆造**。站点上没有的设定就是没有。
5. **星神不公开（仅限历史时代）**：历史时代的文本里禁止「凡人以星神之名行事」类描写
   （如「一国改奉艾拉」「百姓高呼艾拉之名」）。**后日谈里星神的存在已公开，不受此限。**
6. **不要碰专有名词的写法**。库里已统一：白圣女（不是白神女）、长耳族（不是尖耳族）、
   瓦利诺（不是瓦里诺）、艾莉丝（不是艾丽丝）、辛德蕾（不是辛德雷）、工房（不是工坊）。
   你如果发现站点上还有漏网的，按 `fact_edit` 提出来。

## 七、工作循环

```
你（GPT）读站点 → 产出一份东西
        ↓  作者复制
我（本地）落成文件 → 核实 → 出决定卡草稿（写清改什么、依据、影响）
        ↓
作者点头 → 我 apply → 体检 → 重新发布 → 重建站点
        ↓  作者推送
新一版站点上线 → 你重新读，接着下一轮
```

**每一轮结束你都要重读 `/meta.json` 确认指纹变了**，否则说明新版本还没上线。

## 八、我会怎么对待你的提案

| 你的提案 | 我的处理 |
|---|---|
| 站得住 | 转成决定卡草稿，连同依据一起交给作者 |
| 站不住 | **退回并写明为什么**（哪里理解错了、依据不足、还是这条其实是对的），不会闷着改 |
| 与已有裁决冲突 | 引作者的原裁决给你看，说明为什么不能改 |
| `confidence: low` | 我优先核这条，核完告诉你结论 |

**我不会因为是你提的就照改，也不会因为是我写的就不让改。** 谁说的都过同一套校验。
